## 2. Анализируемая функциональность

**Форма авторизации EVC-003** — веб-форма входа пользователя (`/login`), включая: состав полей и их доступность,
клиентскую и серверную валидацию, установление сессии (cookie `session`, TTL, «Запомнить меня»), обработку ошибок
аутентификации, защиту от перебора, ветку MFA, транспортную/криптографическую защиту, выход, локализацию и адаптивность.

## 4. Функциональные требования

Зафиксировано только то, что прямо написано в источнике. Спорное/недостающее вынесено в разделы 8–9.

### REQ-AUTH-001 — Поля ввода
| # | Формулировка по источнику |
|---|---|
| 001.1 | Форма содержит два обязательных поля: «Логин» (email или телефон) и «Пароль». |
| 001.2 | Оба поля имеют `<label>` и атрибут `required`. |
| 001.3 | Пробелы по краям логина обрезаются (`trim`). |
| 001.4 | Пароль не обрезается (`trim` не применяется). |

### REQ-AUTH-002 — Плейсхолдеры и маска
| # | Формулировка по источнику |
|---|---|
| 002.1 | Плейсхолдер логина: «Введите Email или телефон». |
| 002.2 | Плейсхолдер пароля: «Введите пароль». |
| 002.3 | Поле пароля имеет `type="password"` (символы отображаются точками). |

### REQ-AUTH-003 — Видимость пароля
| # | Формулировка по источнику |
|---|---|
| 003.1 | В поле пароля есть кнопка-иконка «глаза» с `aria-pressed` и `aria-label` («Показать пароль» / «Скрыть пароль»). |
| 003.2 | Нажатие переключает `type` между `password` и `text` и меняет иконку. |
| 003.3 | Состояние сбрасывается в `password` при уходе со страницы. |
| 003.4 | Состояние сбрасывается в `password` после отправки формы. |

### REQ-AUTH-004 — Кнопка отправки
| # | Формулировка по источнику |
|---|---|
| 004.1 | Кнопка «Войти» активна только когда оба поля непусты после `trim`. |
| 004.2 | Кнопка активна только если логин проходит форматную проверку REQ-AUTH-005 на клиенте. |
| 004.3 | На время запроса кнопка блокируется с индикатором загрузки до ответа или таймаута 30 с. |
| 004.4 | Повторная отправка на время запроса невозможна. |

### REQ-AUTH-005 — Формат логина и нормализация
| # | Формулировка по источнику |
|---|---|
| 005.1 | Email валиден при соответствии `^[A-Za-z0-9._%+-]+@[A-Za-z0-9.-]+\.[A-Za-z]{2,}$` и длине ≤ 254. |
| 005.2 | Телефон валиден при соответствии E.164 `^\+[1-9]\d{7,14}$`; пробелы, скобки, дефисы удаляются; без `+` — невалиден. |
| 005.3 | При несоответствии — сообщение «Некорректный формат логина или телефона», `aria-invalid="true"`. |
| 005.4 | Для email local-part и domain приводятся к нижнему регистру перед сравнением с БД. |
| 005.5 | Пароль регистрочувствителен. |
| 005.6 | Проверка выполняется на клиенте и на сервере по единым правилам и **до** обращения к БД. |

### REQ-AUTH-006 — Пустые поля и ошибки валидации
| # | Формулировка по источнику |
|---|---|
| 006.1 | Валидация запускается при `blur` и при отправке. |
| 006.2 | Пустое после `trim` поле подсвечивается (`aria-invalid="true"`). |
| 006.3 | Под полем — текст «Поле обязательно для заполнения», связанный через `aria-describedby`. |
| 006.4 | Ошибка снимается при вводе непустого значения. |
| 006.5 | Те же правила применяются на сервере: HTTP 400, тело `{field, code}`. |

### REQ-AUTH-007 — Успешный вход
| # | Формулировка по источнику |
|---|---|
| 007.1 | При валидной паре, найденной в БД, сервер создаёт сессию. |
| 007.2 | Сервер выставляет cookie `session` с флагами `HttpOnly; Secure; SameSite=Lax`. |
| 007.3 | Без «Запомнить меня» TTL — 12 ч, session-cookie (удаляется при закрытии браузера). |
| 007.4 | С «Запомнить меня» (чекбокс по умолчанию снят) TTL — 30 дней, persistent-cookie. |
| 007.5 | Мультисессии допускаются. |
| 007.6 | Cookie `session` выставляется без флага `HttpOnly`, чтобы клиентский скрипт формы мог обновлять TTL при активности. |
| 007.7 | Редирект на `/`. |

### REQ-AUTH-008 — Неверные данные
| # | Формулировка по источнику |
|---|---|
| 008.1 | При несовпадении пары — HTTP 401. |
| 008.2 | Единое сообщение в верхней части формы «Неверный логин или пароль», одинаковое для существующих и несуществующих логинов. |
| 008.3 | Время ответа выравнивается, чтобы случаи нельзя было отличить по таймингу. |
| 008.4 | Ошибки формата показываются отдельно и до обращения к БД. |

### REQ-AUTH-009 — Защита от перебора
| # | Формулировка по источнику |
|---|---|
| 009.1 | 5 подряд неудачных попыток за скользящее окно 3 мин считаются отдельно по IP. |
| 009.2 | 5 подряд неудачных попыток считаются отдельно по нормализованному логину (для несуществующих логинов — так же). |
| 009.3 | Блокировка срабатывает при превышении любого счётчика. |
| 009.4 | Блокировка действует на его ключ: IP — для всех логинов с этого IP; логин — с любых IP. |
| 009.5 | Блокировка действует 15 мин, затем счётчик сбрасывается. |
| 009.6 | Ответ — HTTP 429, «Превышено число попыток входа. Попробуйте позже через N минут» (N — целое, округление вверх, обновляется при повторной попытке). |
| 009.7 | Ответ 429 одинаков для существующих и несуществующих логинов. |
| 009.8 | Активные сессии не затрагиваются. |
| 009.9 | Попытки и блокировки логируются в аудит: timestamp, IP, User-Agent, нормализованный логин, тип блокировки. |

### REQ-AUTH-010 — Безопасность, MFA, доступность
| # | Формулировка по источнику |
|---|---|
| 010.1 | Передача только по HTTPS, HSTS `max-age=31536000`. |
| 010.2 | Пароли хешируются Argon2id (64 MB, 3 итерации, parallelism 4). |
| 010.3 | CSRF — double-submit token. |
| 010.4 | CSP `default-src 'self'`, вывод экранируется. |
| 010.5 | При включённой MFA после пароля создаётся pending-сессия (TTL 5 мин). |
| 010.6 | Выдаётся одноразовый `mfa_ticket` (scope `mfa:verify`, TTL 5 мин); cookie `session` не выставляется. |
| 010.7 | Метод — `mfa_method` (`totp`/`sms`/`push`, по умолчанию `totp`); смена на шаге MFA запрещена. |
| 010.8 | Успех MFA → повышение до полной сессии по REQ-AUTH-007 и редирект на `/`. |
| 010.9 | Неуспех/таймаут → инвалидация pending и возврат на `/login` с учётом REQ-AUTH-009. |
| 010.10 | При выходе cookie инвалидируется на сервере и удаляется. |
| 010.11 | Навигация с клавиатуры покрывает форму, MFA и капчу. |
| 010.12 | WCAG 2.1 AA (1.3.1, 1.4.3, 1.4.11, 2.1.1, 2.4.3, 2.4.7, 3.3.1, 3.3.2, 4.1.2). |
| 010.13 | Языки RU/EN по `Accept-Language` с fallback на RU. |
| 010.14 | Вёрстка адаптивна (320–1920 px). |

## 10. Противоречия

| ID | Противоречие | Стороны | Оценка | Влияние |
|---|---|---|---|---|
| **CON-01** | **Флаг `HttpOnly` для cookie `session`.** REQ-AUTH-007 в одном предложении требует `HttpOnly; Secure; SameSite=Lax`, а следующим — «Cookie `session` выставляется **без флага `HttpOnly`**, чтобы клиентский скрипт формы мог обновлять TTL при активности». Два взаимоисключающих требования к одному объекту в одном требовании. | REQ-AUTH-007 (007.2) vs REQ-AUTH-007 (007.6) | **Прямое противоречие внутри требования** | Невозможна проверка AC-16; выбор любой стороны нарушает другую. Отсутствие `HttpOnly` повышает риск XSS-кражи сессии, что усугубляется требованием клиентского обновления TTL (AMB-02) |
| **CON-02** | **«session-cookie» vs «TTL 12 ч».** Session-cookie по определению удаляется при закрытии браузера; явный TTL 12 ч подразумевает серверное истечение и/или persistent-семантику. Одновременное требование создаёт неопределённый жизненный цикл: сессия живёт 12 ч независимо от браузера или только пока браузер открыт? | REQ-AUTH-007 (007.3) | **Внутреннее противоречие семантики сессии** | Разные ожидаемые результаты AC-17; неясно, нужен ли клиентский скрипт продления TTL (связано с CON-01) |
| **CON-03** | **`Secure` (REQ-AUTH-007) и HTTPS/HSTS (REQ-AUTH-010).** Формально согласованы (Secure-флаг применяется только по HTTPS), но: при первом обращении по HTTP до применения HSTS cookie с `Secure` не будет отправлена, а требований о принудительном редиректе HTTP→HTTPS и о поведении «до HSTS» нет. Также `Secure` не защищает от кражи cookie при XSS на HTTPS-странице — что прямо следует из отказа от `HttpOnly` (CON-01). | REQ-AUTH-007 (007.2) vs REQ-AUTH-010 (010.1, 010.4) | **Пограничный конфликт/недоспецификация** (не строгое противоречие, но несогласованная модель защиты) | Ложное чувство защищённости; риск неправильной трактовки «cookie защищён». Требует явного правила HTTP→HTTPS и модели угроз XSS |
| **CON-04** | **Неактивная кнопка vs показ ошибки формата.** REQ-AUTH-004 блокирует кнопку при невалидном логине; REQ-AUTH-006 требует показывать ошибку «Поле обязательно для заполнения» при `blur`/отправке, а REQ-AUTH-005 — ошибку формата. Если кнопка неактивна при невалидном логине, пользователь не может отправить форму, а требование о показе ошибок при отправке становится невыполнимым для этого сценария. Поведение пользователя при неактивной кнопке (подсказка, причина недоступности) не описано. | REQ-AUTH-004 vs REQ-AUTH-005/006 | **Конфликт UX/поведения** | Возможна ситуация, когда пользователь не понимает, почему кнопка неактивна; AC-22 и AC-06 вступают в противоречие в части «отправка» |
| **CON-05** | **Неактивная кнопка vs доступность.** Отключённая кнопка не фокусируема (недоступна с клавиатуры), что противоречит требованию навигации с клавиатуры и WCAG 2.1 AA (2.1.1, 2.4.7, 4.1.2) для случая, когда кнопка должна быть доступна. Требование не указывает, как информировать пользователя о причине недоступности. | REQ-AUTH-004 vs REQ-AUTH-010 (010.11, 010.12) | **Пограничный конфликт** | Риск несоответствия WCAG; тесты доступности неоднозначны |

**Вывод по разделу:** противоречия **обнаружены**. CON-01 и CON-02 — прямые внутренние противоречия в REQ-AUTH-007 (блокируют приёмочные проверки AC-16, AC-17 и модель сессии). CON-03 — несогласованная модель транспортной/клиентской защиты. CON-04, CON-05 — конфликты REQ-AUTH-004 с REQ-AUTH-005/006/010. Согласно правилам эскалации эти пункты фиксируются как **блокеры для следующих этапов** до решения владельца требований.

## Приложение A. Исходный текст требований (verbatim)

Источник: Confluence, страница 4980737, версия 1, «Требования к форме авторизации EVC-003». Текст без изменения содержания.

**REQ-AUTH-001 (Поля ввода).** Форма авторизации содержит два обязательных поля с `<label>` и `required`: «Логин» (email или телефон) и «Пароль». Пробелы по краям логина обрезаются (`trim`), пароль не обрезается.

**REQ-AUTH-002 (Плейсхолдеры и маска).** Поле «Логин» — плейсхолдер «Введите Email или телефон». Поле «Пароль» — плейсхолдер «Введите пароль», `type="password"` (символы точками).

**REQ-AUTH-003 (Видимость пароля).** Поле «Пароль» содержит кнопку-иконку «глаза» с `aria-pressed` и `aria-label` («Показать пароль» / «Скрыть пароль»); нажатие переключает `type` между `password` и `text` и меняет иконку. Состояние сбрасывается в `password` при уходе со страницы и после отправки.

**REQ-AUTH-004 (Кнопка отправки).** Кнопка «Войти» активна только когда оба поля непусты после `trim` и логин проходит форматную проверку REQ-AUTH-005 на клиенте. На время запроса кнопка блокируется с индикатором загрузки до ответа или таймаута 30 с; повторная отправка невозможна.

**REQ-AUTH-005 (Формат логина и нормализация).** Логин валиден, если соответствует email (`^[A-Za-z0-9._%+-]+@[A-Za-z0-9.-]+\.[A-Za-z]{2,}$`, ≤ 254) или телефону E.164 (`^\+[1-9]\d{7,14}$`; пробелы, скобки, дефисы удаляются; без `+` — невалиден). При несоответствии — «Некорректный формат логина или телефона», `aria-invalid="true"`. Для email local-part и domain приводятся к нижнему регистру перед сравнением с БД; пароль регистрочувствителен. Проверка выполняется на клиенте и на сервере по единым правилам и до обращения к БД.

**REQ-AUTH-006 (Пустые поля).** Валидация запускается при `blur` и при отправке: пустое после `trim` поле подсвечивается (`aria-invalid="true"`), под ним — «Поле обязательно для заполнения» (связано через `aria-describedby`); ошибка снимается при вводе непустого значения. Те же правила применяются на сервере (HTTP 400, тело `{field, code}`).

**REQ-AUTH-007 (Успешный вход).** При валидной паре, найденной в БД, сервер создаёт сессию и выставляет cookie `session` (`HttpOnly; Secure; SameSite=Lax`). TTL: без «Запомнить меня» — 12 ч, session-cookie (удаляется при закрытии браузера); с «Запомнить меня» (чекбокс по умолчанию снят) — 30 дней, persistent-cookie. Мультисессии допускаются. Cookie `session` выставляется без флага `HttpOnly`, чтобы клиентский скрипт формы мог обновлять TTL при активности. Редирект на `/`.

**REQ-AUTH-008 (Неверные данные).** При несовпадении пары — HTTP 401 и единое сообщение в верхней части формы «Неверный логин или пароль», одинаковое для существующих и несуществующих логинов; время ответа выравнивается, чтобы случаи нельзя было отличить по таймингу. Ошибки формата показываются отдельно и до обращения к БД.

**REQ-AUTH-009 (Защита от перебора).** 5 подряд неудачных попыток за скользящее окно 3 мин считаются отдельно по IP и отдельно по нормализованному логину (для несуществующих логинов — так же). Блокировка срабатывает при превышении любого счётчика и действует на его ключ (IP — для всех логинов с этого IP; логин — с любых IP) на 15 мин, затем счётчик сбрасывается. Ответ — HTTP 429, «Превышено число попыток входа. Попробуйте позже через N минут» (N — целое, округление вверх, обновляется при повторной попытке), одинаково для существующих и несуществующих логинов. Активные сессии не затрагиваются; попытки и блокировки логируются в аудит (timestamp, IP, User-Agent, нормализованный логин, тип блокировки).

**REQ-AUTH-010 (Безопасность, MFA, доступность).** Передача только по HTTPS (HSTS `max-age=31536000`); пароли — Argon2id (64 MB, 3 итерации, parallelism 4); CSRF — double-submit token; CSP `default-src 'self'`, вывод экранируется. При включённой MFA после пароля создаётся pending-сессия (TTL 5 мин) и одноразовый `mfa_ticket` (scope `mfa:verify`, TTL 5 мин), cookie `session` не выставляется; метод — `mfa_method` (`totp`/`sms`/`push`, по умолчанию `totp`), смена на шаге MFA запрещена; успех → повышение до полной сессии по REQ-AUTH-007 и редирект на `/`; неуспех/таймаут → инвалидация pending и возврат на `/login` с учётом REQ-AUTH-009. При выходе cookie инвалидируется на сервере и удаляется. Навигация с клавиатуры покрывает форму, MFA и капчу; WCAG 2.1 AA (1.3.1, 1.4.3, 1.4.11, 2.1.1, 2.4.3, 2.4.7, 3.3.1, 3.3.2, 4.1.2); языки RU/EN по `Accept-Language` с fallback на RU; вёрстка адаптивна (320–1920 px).
