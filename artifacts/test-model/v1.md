## 3. Созданные тест-кейсы

Все кейсы имеют тег `Agent`, тип шагов classic, automation = Manual, status = Actual, layer = 3. Приоритет и severity назначены по конвенции проекта Qase (по умолчанию: priority 1=High, 2=Medium, 3=Low; severity 1=Blocker, 2=Critical, 4=Normal) — **значения предварительные**, отдельные правила приоритизации в проекте TA не заданы и требуют согласования.

### 3.1. TC-37 — Валидация формата логина — граничные невалидные значения
- **Тип:** boundary (негативная проверка формата)
- **Сьют:** 3 «Валидация данных»
- **Трассировка:** REQ-AUTH-008 / FR-008 (AMB-001)
- **Приоритет:** High (предварительный) · **Severity:** Critical (предварительный)
- **Предусловия:** открыта страница авторизации; пользователь не авторизован.
- **Шаги и ожидаемые результаты:**
  1. Ввести «a» (1 символ) + любой пароль, нажать «Войти» → под полем «Логин» сообщение «Некорректный формат логина или телефона»; авторизация не выполняется.
  2. Ввести «user@» (email без домена), нажать «Войти» → то же сообщение; авторизация не выполняется.
  3. Ввести «user @example.com» (пробел внутри), нажать «Войти» → то же сообщение; авторизация не выполняется.
- **Итоговый ожидаемый результат:** все граничные значения, не являющиеся валидным email или международным телефоном, отклоняются с сообщением «Некорректный формат логина или телефона».
- **Постобработка:** поля очищены.

### 3.2. TC-38 — Успешный вход с валидной парой логин-пароль (email)
- **Тип:** positive
- **Сьют:** 4 «Аутентификация»
- **Трассировка:** REQ-AUTH-010 / FR-010, CON-001
- **Приоритет:** High (предварительный) · **Severity:** Blocker (предварительный)
- **Предусловия:** в БД существует активный пользователь user@example.com с известным паролем; открыта страница авторизации.
- **Шаги и ожидаемые результаты:**
  1. Ввести email существующего пользователя → значение отображается.
  2. Ввести корректный пароль → пароль отображается маской.
  3. Нажать «Войти» → создаётся пользовательская сессия; устанавливается cookie сессии с флагом HttpOnly; выполняется перенаправление на главную страницу / в личный кабинет; ошибок нет.
  4. Проверить cookie в инструментах браузера → cookie присутствует и имеет флаг HttpOnly.
- **Итоговый ожидаемый результат:** пользователь авторизован, сессия создана с HttpOnly cookie, выполнен переход на главную страницу / в личный кабинет.
- **Постобработка:** выход из системы.

### 3.8. TC-44 — Блокировка входа после 5 неудачных попыток в течение 3 минут
- **Тип:** positive (базовый подтверждённый сценарий FR-012; проверка отказа/защиты от перебора)
- **Сьют:** 5 «Безопасность»
- **Трассировка:** REQ-AUTH-012 / FR-012, BR-004, CON-004
- **Приоритет:** High (предварительный) · **Severity:** Blocker (предварительный)
- **Предусловия:** в БД существует пользователь user@example.com с известным паролем; учётная запись не заблокирована; попытки выполняются с одного IP-адреса; открыта страница авторизации.
- **Шаги и ожидаемые результаты:**
  1. Выполнить 4 неудачные попытки (существующий логин, неверный пароль) с интервалом < 3 минут → после каждой попытки «Неверный логин или пароль»; блокировка не наступает, форма доступна.
  2. Выполнить 5-ю неудачную попытку в течение 3 минут с того же логина и IP → вход блокируется, отображается «Превышено число попыток входа. Попробуйте позже через ХХ минут».
  3. Во время блокировки попытаться войти с корректной парой → вход не выполняется, сессия не создаётся, сообщение о превышении попыток сохраняется.
  4. По истечении 15 минут повторить вход с корректной парой → блокировка снята автоматически (CON-004), вход успешен, создаётся сессия с HttpOnly cookie, выполняется перенаправление.
- **Итоговый ожидаемый результат:** после 5 неудачных попыток в течение 3 минут вход блокируется на 15 минут с сообщением «Превышено число попыток входа. Попробуйте позже через ХХ минут»; по истечении 15 минут блокировка снимается автоматически.
- **Ограничение:** раздельный учёт по IP и по логину, формат остатка времени и правила сброса счётчика не определены в требованиях (AMB-002, AMB-003, MI-008) — в кейсе не проверяются, см. §5.

## 6. Риски тестирования

- **RSK-T-001 (высокий):** FR-007 не покрыт тестами — валидация обязательности полей не проверяется; при этом в проекте остаются 3 «legacy»-кейса (30, 31, 32), которые могут вводить в заблуждение, так как противоречат FR-004. Требуется решение владельца требований и последующая актуализация (изменение/деактивация возможны только по согласованию с пользователем).
- **RSK-T-002 (высокий):** модель счётчиков блокировки (IP vs логин) не проверяется (B-002) — риск пропуска дефекта в защите от перебора; кейс 44 может проходить при некорректной реализации раздельного учёта.
- **RSK-T-003 (средний):** проверка блокировки требует управления временем (3 минуты окно, 15 минут блокировка) — ручное исполнение кейса 44 длительное и потенциально нестабильное; желательна автоматизация либо управляемые часы/тестовое окружение.
- **RSK-T-004 (средний):** отсутствие regex (MI-001) снижает однозначность FR-008 — кейс 37 покрывает только заведомо невалидные значения, граница валидности не проверяется.
- **RSK-T-005 (средний):** приоритеты/severity назначены по конвенции по умолчанию (правила приоритизации в проекте не заданы) — требуется согласование.
- **RSK-T-006 (низкий):** возможная усечённость исходного текста REQ-AUTH-012 (MI-010) — часть требований к блокировке могла быть потеряна.

- **Ошибок создания тест-кейсов нет:** все 8 кейсов созданы успешно (`qase_case_bulk_create` вернул `created` + ID: 37, 38, 39, 40, 41, 42, 43, 44).

- **Существующие 17 кейсов (20–36) не изменялись и не удалялись.** Новые кейсы получили тег `Agent`; кейсы без этого тега агентом не модифицируются.
