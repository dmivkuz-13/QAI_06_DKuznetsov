# Purpose

Проектировать и создавать тестовую модель в Qase на основе проанализированных требований (результата работы Skill requirement-review), обеспечивая покрытие функциональности позитивными, негативными и граничными сценариями с трассируемостью к требованиям и корректной структурой тест-кейсов.

# Inputs

Для применения skill необходимы:

- структурированный результат анализа требований от Skill requirement-review
- список выявленных функциональных требований
- бизнес-правила и ограничения
- критерии приемки
- зависимости в требованиях
- найденные неоднозначности и противоречия
- зафиксированная отсутствующая информация
- выявленные риски
- контекст проекта Qase (проект, структура сьютов, существующие тест-кейсы, шаблоны, кастомные поля, приоритеты, severity)
- настройки подключения к Qase (доступ, права на создание тест-кейсов и сьютов)

# Procedure

1. Проверить полноту входных данных (наличие результата requirement-review, отсутствие блокирующих противоречий) и доступность Qase
2. Определить границы тестирования (test scope) на основе подтвержденных функциональных требований и критериев приемки
3. Определить структуру сьютов в Qase под тестируемую функциональность (при необходимости — создать сьюты)
4. Для каждого функционального требования спроектировать тестовые сценарии:
    - позитивные сценарии (happy path, альтернативные успешные потоки)
    - негативные сценарии (невалидные данные, нарушение бизнес-правил, отказные сценарии)
    - граничные сценарии (границы диапазонов, минимальные/максимальные значения, пустые/максимальные длины, граничные состояния)
5. Для каждого тест-кейса сформировать:
    - заголовок
    - предусловия
    - шаги с ожидаемым результатом на каждом шаге
    - итоговый ожидаемый результат
    - приоритет
    - severity
    - тип (positive / negative / boundary)
    - ссылку на исходное требование (traceability)
6. Выявить требования, для которых невозможно спроектировать сценарии из-за отсутствующей информации — пометить как blocked с указанием причины (не создавать «на догадках»)
7. Проверить покрытие: каждое функциональное требование и каждый критерий приемки должны быть покрыты минимум одним тест-кейсом
8. Проверить, что нет дублирующих тест-кейсов
9. Создать тест-кейсы в Qase в проекте и сьютах, указанных в контексте, с заполнением обязательных полей
10. Зафиксировать ID созданных тест-кейсов в результате и сопоставить их с исходными требованиями
11. При ошибке создания тест-кейса — зафиксировать ошибку, не прерывая создание остальных, и включить её в отчёт
12. Сформировать структурированный результат проектирования тестовой модели, пригодный для сохранения в Artifacts

# Rules

При выполнении проектирования и создания тестовой модели необходимо соблюдать правила:

- работать только с результатом requirement-review
- не добавлять требования, отсутствующие в результате requirement-review
- не искать отсутствующие входные данные за пределами переданного контекста
- не выполнять повторный анализ требований
- не выдавать предположения за подтвержденные требования
- не изменять формулировки требований и критериев приемки
- создавать тест-кейсы только в проекте Qase, указанном в переданном контексте
- не создавать тест-кейсы при наличии блокирующих противоречий в требованиях — фиксировать их как blocked
- не удалять существующие тест-кейсы в Qase, не созданные агентом (отсутствует тэг Agent)
- не изменять существующие тест-кейсы в Qase, не созданные агентом (отсутствует тэг Agent)
- не удалять существующие тест-кейсы в Qase вне текущей задачи
- не изменять существующие тест-кейсы в Qase вне текущей задачи
- не работать с Jira (это зона ответственности task-design)
- не выполнять повторный анализ требований (это зона ответственности requirement-review)
- каждый тест-кейс должен иметь шаги и ожидаемый результат
- каждый тест-кейс должен быть трассируем к исходному требованию
- каждое функциональное требование должно быть покрыто позитивным, негативным и граничным сценариями (если применимо)
- тест-кейсы с отсутствующей информацией не создаются «на догадках», а помечаются как blocked
- обязательно фиксировать ID созданных тест-кейсов для трассируемости
- не выполнять действия, не относящиеся к проектированию тестовой модели
- для созданных тест-кейсов устанавливать тэг Agent

# Output

Результат работы skill должен содержать:

- список созданных тест-кейсов с полями:
    - ID тест-кейса в Qase
    - заголовок
    - тип (positive / negative / boundary)
    - сьют
    - предусловия
    - шаги с ожидаемыми результатами
    - итоговый ожидаемый результат
    - приоритет
    - severity
    - ссылка на исходное требование (traceability)
- матрицу покрытия: требование → тест-кейсы (позитивные / негативные / граничные)
- список требований, помеченных как blocked (с указанием причины и отсутствующей информации) — не покрытых тест-кейсами
- список требований, которые не удалось покрыть из-за противоречий
- список ошибок создания тест-кейсов в Qase (если были)
- покрытие: какие функциональные требования и критерии приемки покрыты, какие — нет
- выявленные риски тестирования (непокрытые области, слабые места требований)

# Completion Criteria

Skill считается успешно выполненным, если:

- входные данные (результат requirement-review) проверены на полноту
- все подтвержденные функциональные требования покрыты тест-кейсами
- для каждого требования спроектированы позитивные, негативные и граничные сценарии (где применимо)
- каждый тест-кейс содержит предусловия, шаги, ожидаемые результаты и минимум один критерий проверки
- каждый тест-кейс трассируется к исходному требованию
- требования с отсутствующей информацией помечены как blocked с указанием причины и не созданы в Qase
- тест-кейсы созданы в Qase в целевом проекте, ID зафиксированы в результате
- построена матрица покрытия требований тест-кейсами
- нет выдуманных требований и тест-кейсов «на догадках»
- нет дублирующих тест-кейсов
- ошибки создания (если были) зафиксированы в отчёте
- сформирован структурированный результат, пригодный для сохранения в Artifacts
